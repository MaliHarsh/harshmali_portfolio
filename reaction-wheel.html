01 / The idea

Use motion to control motion.

A reaction wheel changes the angular momentum of a rotating mass. Accelerating that wheel applies an opposing torque to its supporting body. With suitable sensing and feedback, that torque can correct the body’s tilt.

From January to May 2026, I developed a single-axis self-stabilizing platform using an Arduino, motor driver, and MPU6050 IMU. I integrated the mechanical, electrical, and embedded systems and validated the controller through iterative testing and tuning. The project brought mechanical assembly and control thinking into the same system: the structure supports the rotating mass, the sensor estimates the tilt, and a controller determines how the motor should respond.

Illustrative C++ excerpts connect the control concepts to implementation decisions: timing, tilt estimation, feedback, and actuator limits.

The correction returns to the sensing step: this is a closed loop. The sign of the correction matters as much as its size; the wrong sign amplifies a disturbance instead of reducing it.

Code insight 01 / Illustrative C++

Turn an angle error into a correction.

Design intent: correct the lean while damping the motion, rather than responding to angle alone.

const float error = targetAngle - angle;   // radians
const float pTerm = Kp * error;
const float dTerm = -Kd * angularRate;      // rad/s
const float requested = pTerm + dTerm;
Why this matters

The proportional term responds to displacement from upright; the rate term can reduce overshoot. This PD example assumes a fixed target and a verified motor-command sign.

Physics behind the mechanism

For a wheel with fixed inertia, reaction torque on the body is approximately τ = −Iwαw. A larger wheel inertia produces more reaction torque for a given angular acceleration, but it also changes mass, packaging, and motor demands.

03 / Design thinking

The decisions behind the hardware.

Wheel inertia and packaging

Mass located farther from the axis increases rotational inertia. That creates a design tradeoff between control authority, structural loading, and a compact mechanism.

Sensing and timing

A controller needs a useful angle estimate and a consistent sampling interval. Filtering can reduce noisy measurements, but excess delay makes a fast correction harder.

Code insight 02 / Illustrative C++

Give every measurement a time base.

Design intent: use the elapsed time between samples so angular-rate integration has the correct scale.

const uint32_t now = micros();
const float dt = (now - lastSampleUs) * 1e-6f;
lastSampleUs = now;
if (dt <= 0.0f || dt > maxSampleGap) {
    disableMotor();
    return;
}
Why this matters

Angular rate multiplied by elapsed time gives an angle change. Rejecting an excessive gap avoids integrating as though a delayed sample arrived on schedule. Initialize the timer before the loop; choose the timeout from the intended sampling rate.

Code insight 03 / Illustrative C++

Combine short-term motion with a tilt reference.

Design intent: use the gyroscope for fast changes and the accelerometer to limit accumulated drift.

const float rate = gyroRate - gyroBias;
const float accelTilt = atan2(accelX, accelZ);
const float predicted = angle + rate * dt;
const float blend = filterTime / (filterTime + dt);
angle = blend * predicted + (1.0f - blend) * accelTilt;
Why this matters

This complementary-filter example balances responsiveness and drift correction. The shown axes are illustrative; signs depend on sensor mounting. Initialize angle from a calibrated reading, use consistent radians, and recognize that vibration or linear acceleration can corrupt accelerometer-based tilt.

Actuator limits

Motor torque, current limits, and wheel speed bound what the system can correct. A reaction wheel cannot accelerate indefinitely, so sustained disturbances eventually require a strategy for managing accumulated momentum.

Code insight 04 / Illustrative C++

Respect what the hardware can deliver.

Design intent: bound the request and make loss of valid control data an explicit stop condition.

if (!imuFresh || !isfinite(angle) ||
    fabs(angle) > allowedTilt) {
    disableMotor();
    return;
}
const float limited = constrain(requested, -commandLimit, commandLimit);
applyVerifiedMotorCommand(limited);
Why this matters

Saturation prevents a controller from requesting output beyond its chosen command range. It does not itself enforce motor-current or wheel-speed limits; those need the actual driver and sensing design. The helpers separate hardware-specific behavior from the control logic.

The project combines Arduino-based control, an MPU6050 IMU, a motor driver, and iterative testing. The key engineering challenge is making sensing, computation, and the mechanical response work together.

05 / Reflection

What I gained—and what comes next.

This project helped me connect a mechanical build to a dynamic system. A reaction wheel is not just a spinning component: its inertia, support structure, sensing, and motor response all influence how the mechanism behaves.

The central lesson is to treat mechanics and controls together. A clean control equation still depends on sensor calibration, mounting, timing, and the limits of real hardware.

Next evidence to collect

A useful next step is a time-stamped log of body angle, angular rate, motor command, and wheel speed during controlled tests. That would make it possible to report recovery time, overshoot, and the operating range with evidence instead of visual impressions.

Code insight 05 / Illustrative C++

Make tuning decisions visible.

Proposed next step: capture the response so a change in gains can be assessed against the same test conditions.

if (telemetryDue && telemetryBufferHasSpace()) {
    queueSample(timeUs, angle, angularRate,
                requested, limited);
}
Why this matters

Comparing requested and limited output reveals saturation; plotting angle and angular rate helps distinguish oscillation from slow correction. Buffered, lower-rate logging avoids adding blocking serial output to the control loop.
